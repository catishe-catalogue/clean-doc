## 1. Введение и единый источник правды

Данный документ является обязательным операционным регламентом для всех AI-агентов (и разработчиков), работающих в кодовой базе проекта **«Чистый документ»**.

Любые архитектурные решения, схемы баз данных, контракты API, бизнес-правила и требования к окружению базируются исключительно на [`docs/TECH.md`](./docs/TECH.md).
Если агент сталкивается с противоречием между промптом пользователя/задачей и [`docs/TECH.md`](./docs/TECH.md), приоритет отдается [`docs/TECH.md`](./docs/TECH.md), либо инициируется процедура `CONTRACT GAP` (см. Раздел 14).

## 2. Обязанности агента и строгие запреты (What NOT to Do)

### 2.1. Обязанности агента

1. Следовать строгому порядку вертикальных срезов (Slice order) и модульным границам.
2. Проверять целостность контрактов (Pydantic схемы, DDL базы данных, TypeScript типы) до написания бизнес-логики.
3. Доводить каждую задачу до успешного прохождения полного набора проверок `make gate`.
4. Поддерживать типобезопасность (`mypy --strict`, TypeScript `strict: true`), покрытие тестами и структурированное логирование.
5. Использовать букву `е` вместо `ё` во всех русскоязычных текстах, документации и сообщениях коммитов.

### 2.2. Категорически запрещено (What NOT to Do)

- **НЕЛЬЗЯ хранить секреты в репозитории:** Запрещен хардкод токенов, API-ключей, паролей от БД и приватных ключей. Все секреты передаются исключительно через переменные окружения (`.env`).
- **НЕЛЬЗЯ логировать содержимое документов или персональные данные:** В соответствии с 152-ФЗ в логи разрешено писать только обезличенные UUID задач, размер файлов в байтах и время исполнения. Запрещено логировать текст документов, имена файлов клиентов и личные данные.
- **НЕЛЬЗЯ совершать реальные внешние вызовы в тестах:** В тестах запрещены реальные запросы к ЮKassa, DaData, Selectel S3 и SMTP-серверам. Все внешние сетевые зависимости обязаны изолироваться моками (`pytest-mock`, `respx`) или локальными эмуляторами (MinIO, Mailhog).
- **НЕЛЬЗЯ использовать неконтролируемый Lazy Loading:** Все обращения к базе данных выполняются асинхронно через `asyncpg` / асинхронные сессии SQLAlchemy с явной подгрузкой связанных сущностей (`joinedload` / `selectinload`), предотвращая N+1 проблемы.
- **НЕЛЬЗЯ смешивать слои:** API эндпоинты не содержат прямой SQL-логики или вызовов библиотек парсинга (`Docling`). Вся тяжелая обработка делегируется сервисному слою и воркерам RQ.
- **НЕЛЬЗЯ писать интерфейсные тексты или ошибки для клиентов на английском:** Весь пользовательский UI-текст, подсказки, валидационные сообщения и тексты ошибок для клиентов пишутся строго на русском языке.
- **НЕЛЬЗЯ писать имена идентификаторов на русском:** Имена модулей, функций, переменных, таблиц, колонок БД, маршрутов API и сообщения системных логов пишутся строго на английском языке.
- **НЕЛЬЗЯ коммитить без запуска проверки `make gate`.**

## 4. Обязательный технологический стек

- **Бэкенд:** Python 3.12+, FastAPI, Uvicorn, Pydantic v2, `asyncpg`, `SQLAlchemy 2.0` (async), `redis-py` (async), `aioboto3` (S3 клиент), `rq` (Redis Queue), `structlog` (структурированное JSON логирование).
- **Пакетный менеджер:** `uv` (управление зависимостями через `pyproject.toml` и `uv.lock`).
- **Фронтенд:** Next.js 14 (App Router, Server Components), TypeScript 5+, Tailwind CSS, `shadcn/ui`, `zustand` (клиентское состояние), `@tanstack/react-query` (серверный стейт), `pdfjs-dist` (превью PDF), `lucide-react`.
- **База данных и очереди:** PostgreSQL 18, Redis 7.2.
- **Конвертация и документы:** `Docling` 2.0+ (встроенный OCR: EasyOCR/Tesseract), `PyMuPDF` (`fitz`), CLI утилита `qpdf`, `python-docx`, `openpyxl`.
- **Инфраструктура:** Docker, Docker Compose, Caddy v2 (автоматический TLS/SSL), MinIO (dev хранилище), Selectel S3 (prod хранилище).

## 5. Архитектурные границы (Strict Module Rules)

```text
clean-doc/
  backend/
    app/
      api/v1/endpoints/   # HTTP контроллеры: прием запросов, валидация DTO, вызов сервисов
      core/               # Глобальный конфиг, безопасность, фабрики подключений к БД и Redis
      models/             # SQLAlchemy декларации таблиц
      schemas/            # Pydantic v2 DTO схемы (Request/Response)
      services/           # Чистая бизнес-логика: биллинг, хранилище, постановка задач в RQ
      workers/            # Фоновые воркеры: процессинг Docling, нарезка превью qpdf
  frontend/
    src/
      app/                # Маршруты Next.js 14 App Router, Server Components
      components/         # UI-компоненты: конвертер, превью, модалки оплаты, shadcn
      lib/                # Клиенты API, обвязка EventSource SSE, типы
      store/              # Zustand сторы клиентского состояния
  deploy/                 # Docker Compose и Caddyfile
  docs/                   # Документация проекта (TECH.md, слайсы)
```

### 5.1. Правила слоя API (`backend/app/api/`)

1. Контроллеры не содержат прямых обращений к SQL или долгих вычислений.
2. Принимают строго Pydantic-схемы или `UploadFile`, валидируют входные параметры и передают управление сервисному слою.
3. Возвращают унифицированные JSON-ответы или открывают SSE-стрим `StreamingResponse`.

### 5.2. Правила сервисного слоя (`backend/app/services/`)

1. Сервисы содержат бизнес-правила: проверка лимитов Free-тарифа, генерация Magic Link, отправка задач в очередь RQ, взаимодействие с S3 через `storage_service.py`.
2. Не привязаны к конкретному HTTP-транспорту (могут вызываться из CLI скриптов или тестов без эмуляции HTTP-запросов).

### 5.3. Правила слоя воркеров (`backend/app/workers/`)

1. В Slice 0 воркер запускается как фоновая заглушка (`worker.py`), валидирующая доступность Redis и удерживающая процесс в режиме ожидания (idle), что обеспечивает чистый старт и healthcheck локального docker-compose стека.
2. Начиная со Slice 1, воркеры исполняются в изолированных процессах `rq worker` (`rq worker priority fast heavy --max-jobs=50`).
3. Обрабатывают задачи конвертации: скачивают файл из S3 $\to$ вызывают `qpdf` для нарезки 2 страниц превью $\to$ вызывают `Docling` для разбора структуры $\to$ генерируют `.docx`/`.xlsx` $\to$ загружают результат обратно в S3 $\to$ публикуют событие завершения в Redis Pub/Sub.
4. Ловят все исключения и обновляют статус задачи в PostgreSQL (`status = 'failed'`, `error_message = '...'`).

## 6. Порядок реализации срезов (Slice Order & Procedure)

Реализация функциональности ведется строго последовательно:

```text
Slice 0: Foundation ──> Slice 1: Processing ──> Slice 2: Auth & UX ──> Slice 3: Billing & B2B ──> Slice 4: Deploy & Hardening
```

### 6.1. Алгоритм реализации каждого среза

1. **Проверка требований:** Открыть [`docs/TECH.md`](./docs/TECH.md), изучить контракты, схему БД и ограничения для выбранного среза.
2. **Схемы и миграции:** Объявить модели SQLAlchemy в `models/` и создать миграцию Alembic.
3. **Pydantic схемы:** Зафиксировать DTO в `schemas/`.
4. **Сервисная логика и воркеры:** Реализовать логику в `services/` и задачи в `workers/` с unit-тестами.
5. **API эндпоинты:** Реализовать маршруты в `api/v1/endpoints/` с интеграционными тестами.
6. **Клиентская часть:** Создать компоненты Next.js, хуки TanStack Query и Zustand сторы.
7. **Проверка качества:** Запустить локально команду `make gate`. Исправить все замечания линтеров и тестов.

## 7. Правила тестирования (Testing Rules)

### 7.1. Что тестировать

- **Service Layer (Unit):** 100% покрытие бизнес-логики: проверка дневных лимитов, валидация ИНН, расчет сроков жизни файлов, логика генерации pre-signed ссылок S3.
- **Workers & Parsing (Integration):** Тестирование конвертации на эталонных минимальных PDF-файлах (проверка создания валидных DOCX и XLSX файлов с непустыми таблицами).
- **API Endpoints (Integration):** Проверка кодов ответа FastAPI (202, 400, 403, 404), структуры ошибок `{ "error": string, "code": string }`, корректности заголовков SSE стрима.
- **Frontend (Unit & Component):** Тестирование компонентов дропзоны, валидации ввода ИНН и отображения ошибок с помощью Vitest.

### 7.2. Категорический запрет на реальные внешние вызовы

- В тестах **запрещены** реальные сетевые вызовы к ЮKassa, DaData, Selectel S3 и SMTP-серверам.
- Используются моки (`pytest-mock`, `respx` для HTTP API DaData/ЮKassa) или локальный тестовый MinIO в Docker.

## 9. Правила работы с конвертацией документов (Docling & qpdf)

1. **Валидация на входе:** Перед передачей файла в парсер проверяются Magic Bytes (`%PDF-`). Если файл зашифрован паролем — немедленный возврат ошибки `CORRUPTED_PDF`.
2. **Быстрое превью через `qpdf`:** Для формирования превью первых 2 страниц вызывается легковесная CLI команда:

   ```bash
   qpdf input.pdf --pages input.pdf 1-2 -- preview.pdf
   ```

   Это экономит секунды CPU и гигабайты памяти, не загружая тяжелый ML-пайплайн.
3. **Таймауты задач:** На выполнение конвертации жестко устанавливается лимит `job_timeout = 180` секунд.
4. **Контроль оперативной памяти:** Запрещено создавать глобальные переменные для тяжелых моделей. Процессы воркеров RQ запускаются с параметром `--max-jobs=50`.

## 10. Правила API и HTTP

1. Все эндпоинты возвращают ошибки в строгом JSON формате:

   ```json
   {
     "error": "Описание ошибки на русском языке для пользователя",
     "code": "MACHINE_READABLE_ERROR_CODE",
     "upgrade_url": "/pricing"
   }
   ```

2. SSE-эндпоинт `/api/v1/convert/jobs/{id}/stream` обязан корректно обрабатывать разрыв соединения клиентом (закрывать подписку на Redis Pub/Sub и освобождать ресурсы).
3. Доступ к скачиванию готового файла отдается через временный подписанный S3 Pre-signed URL со сроком жизни не более 15 минут.

## 11. Правила работы с базой данных (Database Rules)

1. **UUIDv4:** Все первичные ключи имеют тип `UUID` с генерацией по умолчанию через `gen_random_uuid()`.
2. **Параметризация:** Категорически запрещено использование f-строк или строковой конкатенации при формировании SQL-запросов (защита от SQL Injection).
3. **Миграции Alembic:**
   - Все изменения структуры БД оформляются миграциями Alembic.
   - Миграции обязаны содержать как метод `upgrade()`, так и корректный `downgrade()`.
4. **Транзакции:** Финансовые операции (подтверждение платежа, генерация счета, изменение тарифного плана) выполняются строго в рамках атомарной транзакции БД.

## 12. Правила разработки фронтенда (Frontend Rules)

1. **Next.js 14 App Router:**
   - По умолчанию все компоненты — Server Components.
   - Директива `'use client'` добавляется только там, где необходим доступ к браузерным API, Drag & Drop событиям или состоянию хуков.
2. **Стилизация:** Исключительно утилитарные классы Tailwind CSS и компоненты библиотеки `shadcn/ui`.
3. **Типобезопасность:** Режим `strict: true` в TypeScript. Запрещено использование типа `any`.
4. **Тексты интерфейса:** Все надписи, кнопки, подсказки и сообщения об ошибках пишутся строго на русском языке.

## 13. Правила инфраструктуры и развертывания

1. **Локальная разработка:** Поднимается одной командой `make dev` через `docker-compose.yml`. Используется MinIO (порт 9000) вместо платного облачного S3 и Mailhog для перехвата писем с Magic Link.
2. **Продакшн контур:** Поднимается на VDS через `docker-compose.prod.yml`. Перед веб-приложением и API устанавливается **Caddy v2**, обеспечивающий автоматический выпуск SSL-сертификатов Let's Encrypt и терминацию TLS 1.3.
3. **Соответствие 152-ФЗ:** В проде используются серверы и S3-бакеты, расположенные строго на территории РФ (Selectel, регион ru-1).

## 14. Регламент расхождения контрактов (CONTRACT GAP Procedure)

Если во время реализации агент обнаруживает, что:
1. В [`docs/TECH.md`](./docs/TECH.md) отсутствует необходимое поле, маршрут, таблица или спецификация;
2. Существующий код или требования противоречат спецификации в [`docs/TECH.md`](./docs/TECH.md);
3. Схема БД или API требует изменений, затрагивающих несколько модулей;

**Агент ОБЯЗАН немедленно приостановить реализацию спорной части и зафиксировать `CONTRACT GAP` в следующем точном формате:**

```text
=== CONTRACT GAP ===
[СЕРВИС / КОМПОНЕНТ]: <Название модуля, например: converter_service>
[ОБНАРУЖЕННОЕ РАСХОЖДЕНИЕ]: <Краткое и точное описание проблемы или недостающей спецификации>
[ИСТОЧНИК В TECH.MD]: <Раздел или ссылка на docs/TECH.md, где обнаружено несоответствие>
[ТЕКУЩАЯ РЕАЛИЗАЦИЯ / КОД]: <Что ожидает код или внешняя система>
[ПРЕДЛАГАЕМОЕ РЕШЕНИЕ]: <Конкретное предложение по обновлению контракта/схемы>
[БЛОКИРУЮЩИЙ ФАКТОР]: <Да / Нет (можно ли продолжать работу над другими частями среза)>
=== CONTRACT GAP ===
```

После публикации блока `CONTRACT GAP` агент согласовывает изменения, вносит правки в [`docs/TECH.md`](./docs/TECH.md) и только затем продолжает написание кода.

## 15. Конвенция коммитов (Commit Conventions)

Все коммиты в репозитории обязаны строго соответствовать стандарту Conventional Commits:

### 15.1. Формат

```text
type(scope): description
```

### 15.2. Правила оформления

- **Язык описания:** Русский язык, строчные буквы.
- **Пунктуация:** Без точки на конце.
- **Буква «е»:** Строго использовать букву `е` вместо `ё` (например: `конвертация`, `переключение`, `подтвержден`).
- **Длина строки:** Максимум 72 символа.

### 15.3. Допустимые типы (Types)

- `feat` — новая функциональность.
- `fix` — исправление ошибки.
- `refactor` — рефакторинг кода без изменения внешней логики.
- `docs` — изменения в документации.
- `chore` — рутинные задачи, обновление зависимостей.
- `style` — правки форматирования, отступов.
- `ci` — настройка CI/CD пайплайнов.
- `perf` — оптимизация производительности.
- `build` — сборка проекта, Makefile, Docker, Caddy.
- `test` — добавление или исправление тестов.

### 15.4. Допустимые области (Scopes)

`infra`, `api`, `worker`, `fe`, `auth`, `billing`, `db`, `docs`, `ci`.

### 15.5. Примеры корректных коммитов

- `feat(worker): добавлен парсинг таблиц pdf через docling`
- `feat(api): реализован sse стриминг статуса конвертации`
- `fix(billing): исправлена проверка подписи вебхука юкассы`
- `docs(tech): обновлена спецификация dadata для b2b счетов`
- `test(api): добавлены тесты лимитов анонимных конвертаций`
- `ci(infra): настроен запуск make gate в github actions`
